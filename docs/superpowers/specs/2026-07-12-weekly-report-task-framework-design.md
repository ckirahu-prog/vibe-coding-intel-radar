# 信息雷达周报 · 任务型框架设计

**日期**：2026-07-12  
**状态**：待用户审阅规格  
**范围**：周报阅读结构、模块职责、卡片字段、条数上限、写作语气；不含采集流水线重写

---

## 1. 问题与目标

### 1.1 用户要完成的事

打开周报后，能快速找到：

1. **值得跟进的机会 / 真实案例**
2. **值得试的 Vibe Coding 技术**（如 Godot-MCP、生图、ai-game-devtools）

每条跟进项须自带：**为什么跟** + **下一步怎么跟**。

### 1.2 当前框架的失败点

现行 A（副业）/ B（游戏）/ C（商业化）/ D（附录）按**情报来源领域**平铺：

- 开篇是「三域摘要 + 本周只做 1 件事」，与「多条跟进短名单」目标错位
- 技术（MCP、工具）埋在 B1 案例表或 D1 工具表，与新闻/游戏案例等权
- 字段细、条目多，读完仍不知跟哪几条
- 用语偏咨询腔 / 大厂腔，技术不多的人费劲

### 1.3 成功标准

- 打开后约 30 秒能指出：2–3 个机会/案例 + 1–2 个技术专名
- 不翻五字段长表也能回答「为什么跟」和「这周下一步」
- 没听说过某个产品的人，靠「一句话背景」不懵
- 正文少行话；术语可在附录词表学习

---

## 2. 设计原则

1. **按阅读任务组织，不按采集分类组织**
2. **先收敛、后展开**：跟进台是主舞台，证据库后置
3. **技术升为一级模块**，不再当游戏案例的附属字段
4. **硬性条数上限**，防止再碎
5. **人话优先**：先场景、后专名；禁用空泛行话

---

## 3. 新模块框架

阅读顺序：

```
A 本周跟进台  →  B 机会与案例  →  C 技术雷达  →  D 游戏方向与制作启发  →  附录（证据与词表）
```

| 模块 | 唯一职责 | 回答的问题 |
|------|----------|------------|
| **A 本周跟进台** | 替读者做第一次筛选与排序 | 这周该盯哪几条？下一步做什么？ |
| **B 机会与真实案例** | 痛点机会 + 已验证赚钱/产品案例 | 哪些需求或案例值得继续研究？ |
| **C Vibe Coding 技术雷达** | 工具、MCP、管线、生图等 | 有哪些技术值得试？怎么试最小一步？ |
| **D 游戏方向与制作启发** | 项目、题材、可复制做法 | 做游戏时题材与制作上可借鉴什么？ |
| **附录** | 证明可信 + 供学习 | 来源、审计、弱信号、术语解释 |

### 3.1 与旧 A/B/C/D 的映射

| 旧结构 | 迁入 |
|--------|------|
| 开篇「本周决策」+「只做 1 件事」 | **淘汰为主 CTA**；可选提示并入 A 某条「下一步」 |
| 旧 A1 强证据机会 | → 新 B1 |
| 旧 A2 弱信号 | → 新 B3（极简）或附录 |
| 旧 A3 需求地图 / A4 竞品 | → 附录（按需）；不挡主线 |
| 旧 B1 中的**技术/MCP/工具** | → 新 **C** |
| 旧 B1 中的**成品游戏/项目** | → 新 D1 |
| 旧 B2 题材 | → 新 D2 |
| 旧 B3 趋势叙事 | → 可压成 D 末 1 段短总结，或并入 A 一句 |
| 旧 C1 / C2 商业化 | → 新 B2（案例）+ 可选并入 A |
| 旧 D1 工具速查 | → **取消重复表**；工具只在 C 出现一次 |
| 旧 D2 词表 | → 附录词表（加强，供学习） |
| 旧 D3 审计 | → 附录 |
| 旧 D4 三域行动 | → 并入 A 各条「下一步」，不再单独三列表 |

## 4. 条数硬上限

| 位置 | 上限 | 细分 |
|------|------|------|
| A 跟进台 | **5–7 条** | 重点跟进 2–3 · 值得收藏 2–3 · 暂不跟进 0–2 |
| B | B1 ≤3 · B2 ≤3 · B3 ≤4 | B3 只标题+一句，不展开表 |
| C | **4–6 条** | 至少 2 条标「可直接试」 |
| D | D1 ≤3 · D2 ≤3 · D3 ≤2 · D4 ≤2 | D4「不建议跟」一句即可 |
| 附录 | 不设阅读配额 | 不进主阅读流 |

技术类（MCP / 生图 / 开发工具等）若当期有素材，**至少占 A 的 1 个名额**；无素材不硬凑。

## 5. 卡片字段

### 5.1 A · 跟进台（最薄）

| 字段 | 约束 |
|------|------|
| 名称 | 可认专名（如 Godot-MCP），禁止空泛标题 |
| 档位 | 重点跟进 / 值得收藏 / 暂不跟进 |
| 类型 | 机会 · 案例 · 技术 · 题材 |
| 为什么跟 | ≤25 字，人话 |
| 下一步 | ≤30 字，可执行 |
| 详情 | → B/C/D 锚点 |

背景可揉进「为什么跟」，不单独占行。

### 5.2 B · 机会 / 案例卡

| 字段 | 约束 |
|------|------|
| **一句话背景** | ≤40 字；没听说过也能懂这是哪类事 |
| 是什么 | 人群 + 场景 |
| 证据 | verbatim ≤40 字 + 来源 + 日期 + 强弱；单源必标 |
| 为什么现在 | 为何值得研究 |
| 可借鉴切口 | 可怎么做；推断须标【推断】 |
| 下一步 | 本周可执行动作 |
| 原文 | URL |

### 5.3 C · 技术判断卡

| 字段 | 约束 |
|------|------|
| **一句话背景** | ≤40 字；先解释它帮人干什么 |
| 解锁什么 | 一句能力，不写新闻口吻 |
| 成熟度 | 可直接用 / 值得试 / 仅观察 |
| 门槛与坑 | 真实限制，人话 |
| 适合什么项目 | 场景匹配 |
| 本周最小试验 | ≤4 小时可完成 |
| 相对上周 | 新增 / 升级 / 无变化 |
| 原文 | URL |

C 内按工作流分子节（有内容才出节，空节省略）：

- C1 写代码与 AI 助手（Cursor、Claude Code、Skills、MCP 客户端侧）
- C2 游戏引擎里动手（Godot/Unity MCP、场景、试玩）
- C3 画面与内容（生图、动画、UI、音频等）
- C4 自动化与发布（流水线、构建、上架相关）

### 5.4 D · 游戏启发卡

| 字段 | 约束 |
|------|------|
| **一句话背景** | ≤40 字 |
| 代表 | 游戏 / 项目名 |
| 玩家为何买账 | 吸引力 |
| 单人+AI 可复用点 | 具体可借鉴什么 |
| 现实规模 | 几周 / 几场景上限 |
| 不要照抄 | 风险一句 |
| 原文 | URL |

D 内部分：

- D1 值得研究的游戏 / 项目
- D2 题材与玩法信号
- D3 可复制的制作方法
- D4 不建议跟的方向（可选）

### 5.5 附录

- 上周条目状态（持续 / 新增 / 降温 / 已验证下一步）
- 弱信号完整列表
- 竞品补充（原 A4）
- 质量说明 + 联网审计（原 D3）
- **词表**（供学习；正文不依赖先背词）

## 6. 写作与可读性（强制）

### 6.1 三条硬规则

1. **先讲人话场景，再出专名**
2. **正文尽量不用行话；必须出现的术语进附录词表**
3. **案例必须有「一句话背景」**，避免没上下文的专名砸脸

### 6.2 禁用 / 改写

| 少写 | 改成方向 |
|------|----------|
| 零集成 / 无集成 / 边界 | 不用接别的软件，自己就能用 |
| 完成定义 / 证据门（无解释时） | 说「做完了」之前先交出测试或截图 |
| 闭环 / 抓手 / 对齐 / 心智负担 | 具体动作描述 |
| 赋能 / 智能化升级 / 核心路径 | 删掉或改成具体结果 |
| 垂直场景 / 变现路径 | 用在什么人、怎么赚钱（直说） |

禁用腔调：咨询腔、大厂 OKR 腔、空泛 AI 营销腔。

### 6.3 目标读者

默认按**技术知识不多、但愿意动手试**的人写。作者自己可看附录词表补课；正文须独立可读。

### 6.4 改写对照（规范示例）

**费劲**：Ambient Memory：Mac 本地+零集成，14 天验证付费 → 读帖拆「无集成」边界  

**好懂**：

- 背景：有人做了个小工具，帮你记住和 Claude 聊过的进度，怕漏跟。
- 为什么跟：据说两周就有大约 50 个付费用户。
- 下一步：打开原帖，看它怎么做到「不用接一堆别的软件」。

## 7. 邮件与生成产物

- 周报仍为**单文件** Markdown → HTML 邮件
- 邮件摘要卡优先渲染 **A 跟进台前 3–5 条**（名称 + 为什么跟 + 下一步），不再以「统计数字 + 只做 1 件事」为主
- 生成规范（`templates/weekly-prompt.md`）须：先产出 A 清单（含技术配额），再填 B/C/D，最后附录
- 版本标识建议升为任务型框架版本号（实现阶段再定具体数字，如 4.0）

---

## 8. 非目标（本期不做）

- 不拆成「简报 + 证据库」两封邮件
- 不重写每日采集 / digest 算法（除非生成规范引用字段需要微调）
- 不做 Web App 阅读器
- 不把附录做成必须阅读的主路径

---

## 9. 实现时主要改动面（代价提示）

| 处置 | 内容 |
|------|------|
| 改造 | `templates/weekly-prompt.md` 结构与写作规则；邮件摘要提取逻辑 |
| 保留 | raw / digest / enrichment 流水线；证据字段作为 B/C/D 详情 |
| 淘汰或降权 | 「本周只做 1 件事」唯一 CTA；D1 工具重复表；技术与新闻等权混在旧 B1 |

半改风险：只加跟进台、旧 A/B/C 顺序与「决策」叙事不动 → 两套主线打架，碎感复发。

## 10. 验收清单

- [ ] A 为文首主舞台，5–7 条，含至少 1 条技术（有素材时）
- [ ] 每条 A 含：为什么跟 + 下一步；专名可认
- [ ] B/C/D 详情卡含「一句话背景」
- [ ] C 独立存在；Godot-MCP 类不主要埋在游戏案例里
- [ ] 条数不超过第 4 节上限
- [ ] 正文通过第 6 节禁用词抽查
- [ ] 词表在附录，正文不依赖先读词表
- [ ] 邮件摘要卡展示跟进短名单而非单一「只做 1 件事」
