# 信息雷达周报 · 任务型框架设计

**日期**：2026-07-12  
**状态**：已批准（2026-07-12）  
**范围**：周报阅读结构、模块职责、卡片字段、条数上限、筛选标准、写作语气、邮件验收；不含采集流水线重写

---

## 1. 问题与目标

### 1.1 用户要完成的事

打开周报后，能快速找到：

1. **值得跟进的机会 / 真实案例**
2. **值得试的 Vibe Coding 技术**（如 Godot-MCP、生图、ai-game-devtools）

跟进项须让人明白：**为什么值得看**，以及按档位给出**试一试 / 观察什么 / 何时再用**——不是每周塞满作业。

### 1.2 当前框架的失败点

现行 A（副业）/ B（游戏）/ C（商业化）/ D（附录）按**情报来源领域**平铺：

- 开篇是「三域摘要 + 本周只做 1 件事」，与「多条跟进短名单」目标错位
- 技术（MCP、工具）埋在 B1 案例表或 D1 工具表，与新闻/游戏案例等权
- 字段细、条目多，读完仍不知跟哪几条
- 用语偏咨询腔 / 大厂腔，技术不多的人费劲
- 缺少整期总量上限与周对周连续性露出

### 1.3 成功标准

- 打开后约 30 秒能指出：2–3 个机会/案例 + 1–2 个技术专名
- 不翻长表也能回答「为什么看」和「这周要不要动手」
- 没听说过某个产品的人，靠「一句话背景」不懵
- 正文少行话；术语可在附录词表学习
- 整期正文（B+C+D）可读完，预计 **8–10 分钟内**
- 同一条信息只在一个主模块展开，不重复

---

## 2. 设计原则

1. **按阅读任务组织，不按采集分类组织**
2. **先收敛、后展开**：跟进台是主舞台，证据库后置
3. **技术升为一级模块**，不再当游戏案例的附属字段
4. **硬性条数上限 + 整期总量上限**，防止再碎
5. **人话优先**：先场景、后专名；禁用空泛行话
6. **少作业、多分流**：真正动手的条目极少；多数是观察或收藏
7. **事实、判断、推测分开标**，不把观察写成铁证

---

## 3. 新模块框架

阅读顺序：

```
A 本周跟进台  →  B 机会与案例  →  C 技术雷达  →  D 游戏方向与制作启发  →  附录（证据与词表）
```

| 模块 | 唯一职责 | 回答的问题 |
|------|----------|------------|
| **A 本周跟进台** | 替读者做第一次筛选与排序 | 这周该盯哪几条？试 / 观察 / 收藏 / 跳过？ |
| **B 机会与真实案例** | 痛点机会 + 已验证赚钱/产品案例 | 哪些需求或案例值得继续研究？ |
| **C Vibe Coding 技术雷达** | 工具、MCP、管线、生图等 | 有哪些技术值得试？怎么试最小一步？ |
| **D 游戏方向与制作启发** | 项目、题材、可复制做法 | 做游戏时题材与制作上可借鉴什么？ |
| **附录** | 证明可信 + 供学习 | 来源、审计、弱信号、术语解释、完整周对周状态 |

### 3.1 与旧 A/B/C/D 的映射

| 旧结构 | 迁入 |
|--------|------|
| 开篇「本周决策」+「只做 1 件事」 | **淘汰为主 CTA**；若需动手，并入 A「本周试一试」某条 |
| 旧 A1 强证据机会 | → 新 B1 |
| 旧 A2 弱信号 | → 新 B3（极简）或附录；超出总量的只留标题+链接 |
| 旧 A3 需求地图 / A4 竞品 | → 附录（按需）；不挡主线 |
| 旧 B1 中的**技术/MCP/工具** | → 新 **C** |
| 旧 B1 中的**成品游戏/项目** | → 新 D1 |
| 旧 B2 题材 | → 新 D2 |
| 旧 B3 趋势叙事 | → 可压成 D 末 ≤80 字短总结，或并入 A 一句 |
| 旧 C1 / C2 商业化 | → 新 B2（案例）+ 可选并入 A |
| 旧 D1 工具速查 | → **取消重复表**；工具只在 C 出现一次 |
| 旧 D2 词表 | → 附录词表（加强，供学习） |
| 旧 D3 审计 | → 附录 |
| 旧 D4 三域行动 | → 并入 A；**仅「本周试一试」写具体动作** |

### 3.2 一条信息只出现一次

- A 中每条必须能在 B / C / D **唯一**详情锚点找到展开
- 同一工具 / 案例 / 题材不得在 B 与 C、C 与 D 各写一整卡
- 关联用「另见 →」一句带过，不复制字段

## 4. 条数硬上限与整期预算

### 4.1 分模块上限

| 位置 | 上限 | 细分 |
|------|------|------|
| A 跟进台 | **5–7 条** | 见 §5.1 档位配额 |
| B | B1 ≤3 · B2 ≤3 · B3 ≤4 | B3 只标题+一句，不展开表 |
| C | **4–6 条** | 「可直接用」按素材质量，**不硬凑至少 2 条** |
| D | D1 ≤3 · D2 ≤3 · D3 ≤2 · D4 ≤2 | D4「不建议跟」一句即可 |
| 附录 | 不设阅读配额 | 不进主阅读流；承接溢出条目 |

### 4.2 整期总量（防「结构好看但仍很长」）

| 约束 | 数值 |
|------|------|
| **B + C + D 正文条目合计** | 最多 **12–15 条**（展开卡；B3 一句条目按半条计或不计入展开配额，实现时统一为「展开卡 ≤15」） |
| **预计阅读时间** | 正文 **8–10 分钟**（不含附录） |
| **溢出** | 超出的只进附录：标题 + 一句话 + 链接，不展开字段表 |
| **宁缺毋滥** | 当期优质内容不足时**少写**；禁止为凑条数灌水 |

### 4.3 技术在 A 中的配额（修正）

技术类（MCP / 生图 / 开发工具等）在通过 §5.0 筛选门槛后，**优先保证 A 中至少 1 条**。  
**不得为满足配额硬塞**不够格的技术条目。

## 5. 筛选标准与卡片字段

### 5.0 A 准入：内部五项判断（不对读者展示分数）

进入 A 前须同时考虑（编辑自检，不必打分公开）：

1. **相关**：与独立游戏 / Vibe Coding / 可小规模尝试相关  
2. **可信**：有可核对来源；单源须自知局限  
3. **新能力或新机会**：读者跟上后，知识或可选路径有实质变化  
4. **现在有用**：本周能试、能观察，或能明确「何时再用」  
5. **成本合理**：试或跟所需时间与技能匹配目标读者  

未过门槛者不进 A；可进 B/C/D 正文或附录。

### 5.1 A · 跟进台（最薄）

**档位（取代「重点跟进 / 值得收藏 / 暂不跟进」）**

| 档位 | 配额 | 「接下来怎么看」写什么 |
|------|------|------------------------|
| **本周试一试** | **最多 1–2 条** | 具体可执行动作（≤4h） |
| **继续观察** | 2–3 条 | 接下来盯什么变化（指标/信号） |
| **先收藏** | 1–2 条 | 适合未来什么情况再拿出来 |
| **本周跳过** | **最多 2 条** | 只写跳过原因；**不进** B/C/D 详情展开 |

| 字段 | 约束 |
|------|------|
| 名称 | 可认专名（如 Godot-MCP），禁止空泛标题 |
| 周对周标记 | **新出现** / **连续第 N 周** / **有重要更新** / **已降温**（名称旁短标） |
| 档位 | 上表四档之一 |
| 类型 | 机会 · 案例 · 技术 · 题材 |
| 为什么看 | ≤25 字，人话 |
| 接下来怎么看 | ≤30 字；按档位写试 / 观察 / 时机 / 跳过原因 |
| 详情 | → B/C/D 锚点（「本周跳过」无此项） |

背景可揉进「为什么看」，不单独占行。  
完整周对周历史仍在附录；A 只露短标，避免附录才有连续性。

### 5.2 B · 机会 / 案例卡

| 字段 | 约束 |
|------|------|
| **一句话背景** | ≤40 字；没听说过也能懂这是哪类事 |
| 是什么 | 人群 + 场景 |
| 证据 | verbatim ≤40 字 + 来源 + 日期 + 强弱；单源必标 |
| 为什么现在 | 为何值得研究 |
| 可借鉴切口 | 可怎么做；**推断须标【推断】** |
| 接下来怎么看 | 与 A 档位一致：试 / 观察指标 / 收藏时机 |
| 原文 | URL |

### 5.3 C · 技术判断卡

| 字段 | 约束 |
|------|------|
| **一句话背景** | ≤40 字；先解释它帮人干什么 |
| 解锁什么 | 一句能力，不写新闻口吻 |
| 成熟度 | 见下表**依据**；不可凭感觉乱标 |
| 门槛与坑 | 真实限制，人话 |
| 适合什么项目 | 场景匹配 |
| 本周最小试验 | 仅「可直接用 / 值得试」需要；≤4 小时；「仅观察」可省略 |
| 相对上周 | 新增 / 升级 / 无变化 |
| 原文 | URL |

**成熟度依据（强制）**

| 档 | 须满足 |
|----|--------|
| **可直接用** | 有安装/使用说明、近期仍有维护迹象、存在可运行示例或明确操作路径 |
| **值得试** | 能跑通主路径，但文档、稳定性或功能不完整 |
| **仅观察** | 主要是演示、概念、或长期未维护 |

C 内按工作流分子节（有内容才出节，空节省略）：

- C1 写代码与 AI 助手（Cursor、Claude Code、Skills、MCP 客户端侧）
- C2 游戏引擎里动手（Godot/Unity MCP、场景、试玩）
- C3 画面与内容（生图、动画、UI、音频等）
- C4 自动化与发布（流水线、构建、上架相关）

### 5.4 D · 游戏启发卡

| 字段 | 约束 |
|------|------|
| **一句话背景** | ≤40 字 |
| 代表 | 游戏 / 项目名 |
| **吸引力** | 见下：事实 vs 判断 |
| 单人+AI 可复用点 | 具体可借鉴什么 |
| 现实规模 | 几周 / 几场景；**无可靠来源须标【估计】** |
| 不要照抄 | 风险一句 |
| 原文 | URL |

**吸引力字段怎么写**

| 证据情况 | 字段写法 |
|----------|----------|
| 有销量、评分、大量玩家评论等 | **玩家为什么愿意玩/买**（可写事实） |
| 仅有帖子展示、榜单收录、开发者自述 | **它可能吸引人的地方【判断】** |
| 制作规模、工期无可靠来源 | 数字旁标 **【估计】** |

禁止在只有 Reddit / itch 上榜时写成像「玩家已经买账」的铁证语气。

D 内部分：

- D1 值得研究的游戏 / 项目
- D2 题材与玩法信号
- D3 可复制的制作方法
- D4 不建议跟的方向（可选）

### 5.5 附录

- 上周条目**完整**状态（持续 / 新增 / 降温 / 已验证下一步）——A 短标的详细版
- 弱信号完整列表；正文溢出条目（标题+一句+链接）
- 竞品补充（原 A4）
- 质量说明 + 联网审计（原 D3）
- **词表**（供学习；正文不依赖先背词，但正文首次出现仍须顺手解释）

## 6. 写作与可读性（强制）

### 6.1 三条硬规则

1. **先讲人话场景，再出专名**
2. **正文尽量不用行话；必须出现的术语进附录词表，且正文首次仍要解释一句**
3. **案例必须有「一句话背景」**，避免没上下文的专名砸脸

### 6.2 可检查的人话规则（写完自检）

- 每句话尽量只表达**一件事**
- 连续列举不超过**三项**
- 专名首次出现写成：`MCP（让 AI 能调用其他软件的办法）` 这类「名 + 括号人话」
- 不用「只有名词、没有动作」的空标题
- 写完自问：**完全没听说过这个产品的人，是否知道它帮谁做什么？**
- 事实 / 【判断】 / 【推断】 / 【估计】标记齐全，不混用

### 6.3 禁用 / 改写

| 少写 | 改成方向 |
|------|----------|
| 零集成 / 无集成 / 边界 | 不用接别的软件，自己就能用 |
| 完成定义 / 证据门（无解释时） | 说「做完了」之前先交出测试或截图 |
| 闭环 / 抓手 / 对齐 / 心智负担 | 具体动作描述 |
| 赋能 / 智能化升级 / 核心路径 | 删掉或改成具体结果 |
| 垂直场景 / 变现路径 | 用在什么人、怎么赚钱（直说） |

禁用腔调：咨询腔、大厂 OKR 腔、空泛 AI 营销腔。

### 6.4 目标读者

默认按**技术知识不多、但愿意动手试**的人写。作者自己可看附录词表补课；正文须独立可读。

### 6.5 改写对照（规范示例）

**费劲**：Ambient Memory：Mac 本地+零集成，14 天验证付费 → 读帖拆「无集成」边界  

**好懂**（档位示例：继续观察 / 先收藏）：

- 背景：有人做了个小工具，帮你记住和 Claude 聊过的进度，怕漏跟。
- 为什么看：据说两周就有大约 50 个付费用户。
- 接下来怎么看：打开原帖，看它怎么做到「不用接一堆别的软件」；暂不必自己重做。

**本周试一试**示例（Godot-MCP）：

- 背景：Godot 是做游戏的引擎；MCP 让 AI 助手能直接在引擎里动手，不只聊天给代码。
- 为什么看：可以少切好几层窗口，试着让 AI 帮你摆场景、点运行。
- 接下来怎么看：装上，自己做一次「加个节点 → 运行 → 截张图」（≤4h）。

## 7. 邮件与生成产物

- 周报仍为**单文件** Markdown → HTML 邮件
- 邮件摘要卡优先渲染 **A 跟进台**（优先「本周试一试」+「继续观察」，共约 3–5 条）：名称 + 为什么看 + 接下来怎么看；不再以「统计数字 + 只做 1 件事」为主
- 生成规范（`templates/weekly-prompt.md`）须：先按 §5.0 筛候选 → 产出 A（含技术优先规则）→ 再填 B/C/D（遵守总量）→ 溢出与审计进附录
- 版本标识建议升为任务型框架版本号（实现阶段再定具体数字，如 4.0）

### 7.1 交付与降级

| 场景 | 要求 |
|------|------|
| QQ 邮箱内 A→详情锚点 | 实现时验证**真的可点**；不可靠则改为「见下文 · 模块 X」明文指引 |
| 手机窄屏 | 卡片/表格须可读；避免过宽多列表格作主路径（B2 旧九列表须拆掉或简化） |
| 摘要卡解析失败 | **降级**：只显示周期 +「请打开正文看本周跟进台」；不猜测条目、不回退成「只做 1 件事」假数据 |
| 优质内容不足 | 少写；A 可少于 5 条；禁止灌水 |

### 7.2 上线前样稿对比

用既有一期素材（如 **2026-W28**）按本规格生成一份新版样稿，与原版做 **30 秒阅读对比**：能否更快说出 2–3 个机会/案例 + 1–2 个技术名，且语气是否更易懂。不通过则先改规范再改流水线。

## 8. 非目标（本期不做）

- 不拆成「简报 + 证据库」两封邮件
- 不重写每日采集 / digest 算法（除非生成规范引用字段需要微调）
- 不做 Web App 阅读器
- 不把附录做成必须阅读的主路径
- 不向读者展示 A 准入打分过程

## 9. 实现时主要改动面（代价提示）

| 处置 | 内容 |
|------|------|
| 改造 | `templates/weekly-prompt.md` 结构、筛选、写作与标记规则；邮件摘要提取逻辑；窄屏友好表格 |
| 保留 | raw / digest / enrichment 流水线；证据字段作为 B/C/D 详情 |
| 淘汰或降权 | 「本周只做 1 件事」唯一 CTA；D1 工具重复表；技术与新闻等权混在旧 B1；为凑数的技术配额 |

半改风险：只加跟进台、旧 A/B/C 顺序与「决策」叙事不动 → 两套主线打架，碎感复发。  
另一风险：A 每条都写「动手下一步」→ 作业过载；须严格执行四档分流。

## 10. 验收清单

### 结构与配额

- [ ] A 为文首主舞台，5–7 条（优质不足时可更少）
- [ ] A 档位符合配额：试一试 ≤2 · 跳过 ≤2；「接下来怎么看」与档位匹配
- [ ] 技术在过门槛后优先占 A ≥1 条；无硬塞
- [ ] B+C+D 展开卡合计 ≤15；预计阅读 8–10 分钟；溢出仅在附录
- [ ] 同一条信息仅一个主模块展开；A 每条有唯一详情锚点（跳过除外）
- [ ] C 独立存在；Godot-MCP 类不主要埋在游戏案例里
- [ ] A 名称旁有周对周短标；完整状态在附录

### 可信与标记

- [ ] B/C/D 详情卡含「一句话背景」
- [ ] 成熟度有依据；吸引力区分事实 / 【判断】；规模无据标【估计】
- [ ] 推断标【推断】；单源必标

### 可读与邮件

- [ ] 正文通过 §6.2 / §6.3 抽查；专名首次有人话解释
